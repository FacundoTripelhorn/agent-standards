# Size and complexity thresholds

Each limit is the default of the standard linter for that language, so the
rule an agent reads in `code.md` matches what the linter reports, and
nobody has to defend a number we made up.

CI applies them as a **ratchet**: a file or function that is already over a
limit may not grow, and anything new must fit. Old debt never blocks a
change; new debt does.

## Python (ruff, with pylint's rules)

| Limit | Value | Rule | Source |
|---|---|---|---|
| Lines per module | 1000 | pylint `C0302 too-many-lines` (`max-module-lines`) | pylint 4.1.3 source, `checkers/format.py` |
| Statements per function | 50 | ruff `PLR0915` (`lint.pylint.max-statements`) | `ruff config` 0.17.3 |
| Cyclomatic complexity | 10 | ruff `C901` (`lint.mccabe.max-complexity`) | `ruff config` 0.17.3 |
| Branches per function | 12 | ruff `PLR0912` (`max-branches`) | `ruff config` 0.17.3 |
| Arguments per function | 5 | ruff `PLR0913` (`max-args`) | `ruff config` 0.17.3 |
| Returns per function | 6 | ruff `PLR0911` (`max-returns`) | `ruff config` 0.17.3 |
| Nested blocks | 5 | ruff `PLR1702` (`max-nested-blocks`) | `ruff config` 0.17.3 |
| Line length | 88 | ruff `E501` (`line-length`) | `ruff config` 0.17.3 |

Python has no standard "lines per function" limit; statements and complexity
play that role.

## TypeScript / JavaScript (ESLint core)

| Limit | Value | Rule | Source |
|---|---|---|---|
| Lines per file | 300 | `max-lines` | ESLint 9.39 source, `lib/rules/max-lines.js` |
| Lines per function | 50 | `max-lines-per-function` | ESLint 9.39 source |
| Cyclomatic complexity | 20 | `complexity` | ESLint 9.39 source |
| Nesting depth | 4 | `max-depth` | ESLint 9.39 source |
| Parameters | 3 | `max-params` | ESLint 9.39 source |
| Cognitive complexity | 15 | `sonarjs/cognitive-complexity` | eslint-plugin-sonarjs docs; Sonar's default for most languages |

ESLint counts blank lines and comments by default (`skipBlankLines` and
`skipComments` are `false`). We keep that default so the script and ESLint
agree.

React components: `max-lines-per-function` counts a component as one
function. A component over 50 lines is the signal to extract hooks and
subcomponents; that is the intent, not a false positive.

## C# (Sonar / .NET analyzers)

| Limit | Value | Rule | Source |
|---|---|---|---|
| Lines of code per file | 1000 | Sonar `S104` | Sonar's default "for most languages"; not confirmed on the C# rule page |
| Lines of code per method | 80 | Sonar `S138` | SonarSource community, C# rule (default 80) |
| Cognitive complexity | 15 | Sonar `S3776` | Sonar FAQ: 15 for most languages (25 only for C/C++/Objective-C) |
| Cyclomatic complexity | 25 | .NET `CA1502` | Microsoft Learn, CA1502 (off by default) |

Sonar counts lines of code only (no blank lines or comments).

Is 80 too low for Unity? Measured on CoastKids (1,743 runtime and editor
methods, counting code lines only, as Sonar does): median 10, 90th percentile
32, 95th 46, 99th 84. Only 20 methods (1.1%) are over 80, and they are the
ones already flagged in review (`BuildHud`, `LateUpdate`, `StepTalkAndChallenge`).
Raising the limit to 100 would only drop 5 of them; to 120, 12. So 80 stays.

Unity cases that are real:
- Scene builders and layout tables are data more than logic. Move them to
  ScriptableObjects or prefabs, or list them in `size-exceptions.txt` with
  the reason (7 of the 20 long methods in CoastKids are builders).
- `Update`, `LateUpdate` and `FixedUpdate` attract code. Keep them as a short
  sequence of named calls (`ApplyFootLock()`, `BlendClips()`).

## What the shared check measures

The shared CI check measures file size and function size with the units
above (statements for Python functions, lines for TypeScript, lines of code
for C#). Complexity, nesting and parameter counts are left to each
language's linter in `just check`. Function size is not checked in test
files: a test suite is one long `describe` callback by design. Their file
size still is.

## Exceptions

`size-exceptions.txt`, one path per line with a reason:

```
Assets/Game/Park/MuelleBuilder.cs  # scene data, moving to ScriptableObjects in #123
src/generated/api.ts               # generated by openapi-typescript
```

A path listed there is reported but never fails CI. Adding a path is a
reviewed change like any other.

## How the numbers were checked

- ruff: `uv run ruff config <setting>` on ruff 0.17.3.
- ESLint: defaults read from `node_modules/eslint/lib/rules/*.js`, ESLint 9.39.4.
- pylint: `max-module-lines` read from the pylint 4.1.3 wheel (`pylint/checkers/format.py`).
- Sonar and .NET: rule pages and SonarSource community answers (see
  sources in the PR that introduced this file). The C# file-length default
  is the least certain number here.
